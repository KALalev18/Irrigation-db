# Index benchmark

Generated by `npm run bench` on 2026-10-22.

**Setup:** PostgreSQL 16.14 on x86_64-pc-linux-musl in Docker on a local machine. Table with
3,000,000 rows (50 sensors x 60,000 readings),
inserted in time order so each sensor's rows are spread across the table.

**Query:** `SELECT * FROM readings WHERE sensor_id = $1 ORDER BY recorded_at DESC LIMIT 100`

**Method:** `EXPLAIN (ANALYZE)` execution time, 300 runs per index after 30 warm-up runs,
rotating through sensors. Times are server-side and exclude network and Prisma overhead.

| Index | Median | p95 | Plan |
| --- | --- | --- | --- |
| `(sensor_id)` | 61.143 ms | 86.944 ms | Limit -> Gather Merge -> Sort -> Bitmap Heap Scan -> Bitmap Index Scan using readings_sensor_id |
| `(sensor_id, recorded_at DESC)` | 0.185 ms | 0.307 ms | Limit -> Index Scan using readings_sensor_id_recorded_at |

Median execution time dropped by **99.7%**. With the single-column index Postgres
reads all of the sensor's rows and sorts them; the composite index returns them already in order,
so it stops after 100 rows.

**Bulk insert:** 100,000 rows into `sensor_readings` through Prisma `createMany`
in batches of 1,000 took 12.78 s (one run, rolled back afterwards).
